# OUT_OF_SCOPE — openviking-adopt plan

Agnostic-spec capture of things observed while working this plan but not acted on (MASTER_PLAN
§4.3). WHAT + WHY, never HOW — no prescribed solution, no code excerpts. Always-writeable
regardless of scope. Reviewed at scope-closing checkpoints: each entry gets promoted into
SCOPE.md, escalated into INVENTORY.md, archived as won't-fix, or deferred forward.

Format per entry: date · area/file · one-line problem · severity guess · next-touch pointer.

---

- **2026-09-21 · Obsidian vault decision surfaces (`lib/obsidian-{decision-notes,session-notes,summarizer,link-checker}.mjs`)** · Block 3 excludes superseded decisions from recall (injector, decision-FTS channel) and from MEMORY.md, but the vault note generators still list every decision row, so a superseded decision keeps a note beside its successor. · Severity: low (browsing surface only; recall is correct) · Next touch: a small follow-up that renders supersession in the decision note (a "superseded by [[…]]" line) rather than hiding the row.
- **2026-09-21 · `memory.extracted` event payload** · The flush result now carries the typed-merge counts (`entities_new`, `aliases_resolved`, `decisions_superseded`, `known_entities`), but `workspace-bin/memory-daemon.mjs` `emitExtractEvent` copies named fields only and `packages/event-schemas` does not declare them, so the watcher cannot see them yet. Step 3.2's runtime Verify therefore reads the tables, not the event. · Severity: low · Next touch: extend the event schema + emitter in a schema-bump step.
- **2026-09-21 · consolidation archive vs aliases** · When consolidation archives an entity (`entities_archived`) its `entity_aliases` rows are cascade-deleted (FK ON DELETE CASCADE), so a resurrected entity comes back without its aliases. · Severity: low · Next touch: archive aliases alongside the entity in `lib/consolidation.mjs` when Block 3 closes on the node.
- **2026-09-21 · LoCoMo memory-quality benchmark** · The review recommended running LoCoMo against the inject server; OpenViking's `benchmark/` harness is under its AGPL root. Needs a live LLM + embedder, so it cannot run in the authoring container. · Severity: medium (no memory-quality baseline exists) · Next touch: a separately scoped benchmark step on the node, with a license check on any reused harness code.
- **2026-09-26 · no probe exercises the knowledge MCP server** · The stdio server has been dead on the node since the live checkout switch at 2026-09-21 10:54 EDT, and no check identified it. Nothing starts `lib/mcp-knowledge/server.mjs` or completes an MCP handshake with it. node-watch's `mem.knowledge_index` turns BROKEN when `.knowledge.db`'s `last_index_time` is over 2 h old, but the server only runs as a child of a Claude Code session, so that check is also red on any node idle for 2 h and cannot tell a dead entry point from no sessions. The failure itself (exit 0, no output) looks like a clean stop. The 2026-09-21 runtime Verify for 1.1 and 2.1 ran `probe.mjs`, which calls `core.mjs` and `directory-summaries.mjs` directly, so both passed with the MCP entry point broken. · Severity: medium (a whole tool surface can drop out of every session unnoticed) · Next touch: the node-watch/acceptance probe set, and whoever next writes a Verify for an MCP tool.
- **2026-09-26 · node runtime copy of `web-fetch.mjs` (`~/.openclaw/workspace/bin/`)** · The deployed file is a 65-line copy that predates the 2026-09-06 SSRF guard (P5-7): it hands any agent-supplied URL to Playwright with no private-address, metadata or `file://` refusal, and `config/harness-rules.json` directs agents to it when WebFetch fails. The repo's `workspace-bin/web-fetch.mjs` carries the guard, so this is deploy drift, not a code defect. · Severity: high (a remediation the repo records as landed is absent where it runs) · Next touch: whoever deploys the 2026-09-06 remediation to `~/.openclaw` (CLAUDE.md names it the operator's step).
- **2026-09-26 · one knowledge index pass per Claude Code session** · Every session that loads `.mcp.json` starts its own knowledge server. Each server runs an index pass at startup and then every 5 minutes, all against the same `.knowledge.db` and the node's single Ollama. Since 2026-09-21 a pass also asks the LLM for directory abstracts. On 2026-09-26 three passes wrote 0, 1 and 2 abstracts; the other calls ran into the 120 s wall. Under that concurrent load the D9 session saw the memory daemon's boot-time `.knowledge.db` integrity scan take about 3 min 40 s. Each additional open session adds its own pass, and each server loads its own copy of bge-m3 (about 2 GB) for its first search. Startup no longer waits for the pass (2026-09-26), so this is load, not an outage. · Severity: medium (Ollama contention with extraction; RAM when several sessions are open) · Next touch: whoever scopes Block 2.2's runtime closure or the knowledge server's process model.
